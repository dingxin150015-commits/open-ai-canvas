# 系统模型目录与执行资格统一修复方案

状态：`deployed_preverified_edge_pending`。用户批准后已完成实现、预验证和部署；主程序ad3efa10，Gemini文本插件收尾cc7d0b63。最终实施、验证、恢复点和Edge清单见MODEL_CATALOG_UNIFIED_REPAIR_20260913.md。以下保留设计过程；实际目录贡献采用contributes.providers[].modelCatalog，与该Provider共享生命周期。未执行用户Edge或真实生成。

## 1. 已确认事实与边界

- 实际采用的官方架构基线371bc68已有统一protocol.Adapter/Registry、Manifest.contributes.providers和管理模型配置链路。当前执行插件已经走该架构，不应另建Gemini执行器注册体系。
- 当前模型发现补全仍为service静态注册bailian.New的另一条生命周期；目录中的静态supportStatus直接控制管理编辑和任务准入。官方目录事实、项目支持程度、用户配置和运行插件状态混用，是问题核心。
- 本地64015db3/62cf5d83把通用发现置planned并同时禁止前后端编辑；手工新增却会置ready。相同模型因添加方式不同得到不同资格。现有手工新增仍有协议/能力验证，并非完全无校验；但验证与目录只读策略不对称。
- 百炼补充目录当前80条：图片1 ready/1 planned，视频11 ready/67 planned。它不是百炼全部模型目录，也不包含文本模型补充条目；通用上游返回而未补全的百炼文本/新模型仍默认planned。
- 已有七模型及登记视频快照为ready。wan2.7-image-pro、wan2.7-videoedit、wan3.0-video-prime等静态planned仍被锁。图片插件明确仅接受qwen-image-3.0-pro，视频插件只接受已登记家族/ID，不能解除UI禁用后声称这些其他模型已可执行。
- 百炼识别目前依赖DashScope/MAAS主机，代理自定义域名不会自然获得同样补全；反过来也不能仅按模型名推断任意渠道为百炼或套原生协议。
- 页面100条/页与上游API分页独立；已有代码未消费Gemini nextPageToken，但用户本次实际是否漏模型未确认。不得以50条截图作为漏页确证。
- 本轮依据当前源码、固定已采用上游对象及本地百炼合同/插件清单。不是对尚未采用的最新远程主线或所有上游模型实际可用性的声明。

## 2. 推荐原则：发现提供事实，插件提供执行合同，宿主统一决策

不全面回滚本地安全能力；保留显式价格、模型专属输入限制、任务/恢复、资源物化和安全出站。也不再给每个厂商增加宿主静态白名单来绕过只读。

不把新增一个待配置枚举当最终方案。分离四种事实，尽量派生显示结果而非维护多个相互同步的数据库布尔量：

1. **发现事实**：来源/版本、上游ID、方法/操作、文档推荐、完整性；未知不是明确不支持，目录静态planned不是永久执行禁令。
2. **管理员配置**：协议、精确上游ID、能力参数、价格档、启用开关。仍是现有ChannelModel及其规格价格，不改逻辑模型业务含义。
3. **执行合同**：当前已安装且允许当前场景的插件，对精确模型/兼容协议、操作和输入输出限制的结构性支持。
4. **账号实测结果**：权限/额度/真实调用结论，与前三项分开；配置校验成功不冒称调用通过，也不强制付费调用才能保存。

目录里记录的支持评估应保留来源与理由，默认未知而非项目planned。已有明确废弃/禁用政策继续阻断执行；静态旧planned只有被新的有效执行合同和明确配置取代后才可放行，不批量改ready。

## 3. 同一后端配置和执行资格判定

在现有service与effectiveChannelModelCapability/协议Registry上建立单一可复用评估入口，返回结构化结果与原因；命名待实施确定，不声称已存在：

- 配置完整性与错误字段；协议及模型合同匹配证据。
- canEditConfiguration、canEnable、canExecute、可用于哪些surface/operation，以及阻断原因码/修复提示。
- 当前插件/配置版本供缓存失效与审计关联；不持久化易过期的canExecute真值。

保存草稿/编辑不以ready为前置；允许修正或保存仍停用的不完整候选。启用/发布/测试/真实请求更严格，需执行器可用、精确配置合法、所需价格明确、管理员/用户有权、渠道有效。生成前还必须做请求级媒体/参数/额度校验。

手动新增、目录导入后配置、编辑、批量启用、逻辑模型预览/报价/路由、任务入队与worker执行都复用同一结论，消除手工ready与导入planned两条路径。前端只展示后端权限和原因，不再用supportStatus枚举决定整个Form inert。

协议仅有image/text类别不足以保证模型可执行。必须区分普通文本、Agent工具调用、系统队列、自定义中转等路径；Gemini文本当前存在AgentAvailable及AgentRequests要求，应专项审计，不能只看协议出现在下拉框。

## 4. 在上游插件合同内扩展，而非新建平行系统

- 建议扩展现有Manifest的模型匹配/能力描述，以及可选目录贡献，例如contributes.modelCatalogs。准确schema和版本由实现前合同测试确定；当前Manifest尚无此能力，不能假称直接可用。
- 原生模型专属适配器采用精确/受约束模型规则；通用兼容协议采用插件明确声明的兼容模式。新自定义模型ID可由管理员选兼容协议并通过结构校验，但不会获得“原厂精确认证”的假标记。
- 模型规则与请求校验共用可复用的纯合同定义。禁止在目录JSON、宿主Go、前端TS、插件表达式各手写一份互不校验的支持白名单；跨语言需要投影时从同一版本化来源生成并做一致性测试。
- 静态百炼文档目录可以继续作为发现资料；其中模型执行资格由插件合同导出/校验，不再独立控制编辑与执行。厂商资料与执行合同分工，不要求把外部文档全文塞入执行插件。
- 各贡献由现有插件包加载/启停/卸载生命周期产生注册视图；协议与目录可分类型视图，但不能各自维护一套管理员开关或独立加载器。
- 新字段需显式版本/最低宿主能力校验，旧宿主不能忽略必需合同字段后继续执行。原有插件无需为不使用的新能力重写；不为旧缺陷增加永久平行兼容路径。
- 插件停用后保留发现记录和用户配置，执行资格立即失效且提示原因；重启/启用恢复资格评估，不自动启用模型或改价。注册表变化使模型目录/逻辑路由缓存失效。

## 5. 发现与分页：窄协议驱动、安全宿主执行

- 统一发现驱动接口：OpenAI兼容、Gemini原生等按目录协议选择，不按渠道显示名称猜测。单一GET分页引擎消费驱动产生的下一页游标。
- 主机只执行受控同源目录GET：复用出站校验、鉴权注入、超时/响应大小/总模型数/总页数限制、取消和重复游标检测。禁止插件自行HTTP、任意nextURL、把凭据写进URL/日志。
- Gemini解析name、displayName、supportedGenerationMethods和nextPageToken；generateContent不能单独判定为图片或文本完整支持，多模态/歧义匹配由精确合同或管理员配置解决。
- 不支持/models的渠道允许手工配置；自定义代理域名不能仅因不匹配官方主机就锁死，也不能仅因名字相似就套用厂商协议。
- 拉取失败/部分结果需明确完整性状态，不覆盖已配置字段、不据缺项删除/停用存量模型；上游元数据只作待确认建议，不允许覆盖已选执行协议和价格。

## 6. 存量修复与范围控制

- 先只读盘点Gemini/百炼/其他渠道记录，按未配置、人工配置、明确不支持、已有业务引用分类；不输出真实凭据。
- 保留现有模型/逻辑模型/路由ID、价格和版本、启用状态、订单及引用。已有Qwen用户配置必须原样保持。
- 对源于通用未知目录的planned候选恢复受校验配置入口；有效的新插件合同可解开已完成支持但静态目录未更新的模型。真正缺模型合同的条目仍不可调用。
- 未配置项可以原地补齐建议；已有配置不自动改写。当前catalogMayBeEnriched把已配置项全部跳过：应保持配置保护，同时让执行资格依据实时插件重新计算，避免新增适配永远无法被已有记录识别。
- 首选最小字段改动与派生状态；若来源/版本或字段语义变更确需Schema，则单一版本迁移、备份/克隆验证并同步backend-database文档，不直接改生产库support_status。
- 本修复覆盖通用配置机制及Gemini已由现有执行器支持的合同接入，不自动实现当前68条planned百炼模型的新推理/媒体算法。未支持能力应列精确差距，作为后续插件能力开发，不混成目录修复。
