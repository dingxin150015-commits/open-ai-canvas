API协议开发必须遵循的原则和流程，从DashScope视频协议开发中吸取的教训。

**核心原则：**

1. **文档是唯一真理源** - 绝不凭记忆或经验写API调用代码，必须逐字对照官方文档验证每个端点路径、HTTP方法、Header、参数格式。

2. **先验证后实现** - 开发前必须先用curl测试API端点可用性，确认返回格式正确，记录实际响应示例，再开始编码。

3. **实际调用验证** - 代码逻辑测试不足以保证正确性，必须实际调用API验证，至少跑通一个完整流程再交付。

**标准开发流程（SOP）：**

Phase 0: 文档研读（30分钟）
- 完整阅读API文档
- 创建端点检查清单：URL路径、HTTP方法、Headers、请求/响应格式
- 标记所有疑问点

Phase 1: API验证（30分钟）
- 获取测试API Key
- 用curl测试每个端点
- 验证路径、参数、返回格式正确
- 记录成功的curl命令作为参考

Phase 2: 最小Demo（1小时）
- 实现最基础调用
- 本地运行测试
- 确认至少一个场景成功

Phase 3: 完整实现（2-3小时）
- 扩展所有功能
- 边界条件和错误处理
- 代码审查：对照文档检查每个字符串常量

Phase 4: 集成测试（1小时）
- Docker构建部署
- **验证容器加载了新二进制**（见 [[docker-verify-deployment-before-testing]]）
- 端到端验证

Phase 5: 文档交付（30分钟）
- 标记已验证和未验证的部分
- 列出已知限制

**4. 返回格式必须与既有实现一致** - 新增协议时，返回给上层的数据结构必须比照同类既有协议（字段名单复数、嵌套层级、必带字段），不能自行设计。

**5. 新协议要遍历所有调用入口** - 一个能力往往有多个前端入口（画布节点、创作页、项目页等），有的走后端任务队列、有的前端直连。新增协议时必须逐个入口确认覆盖，不能只验证其中一条路径。

**Why:** 2026-08-21~22 DashScope 视频协议开发中连续踩坑：
- 未严格对照文档导致 API 路径缺少 `/api/v1` 前缀
- 返回格式用了 `videos` 数组，而既有 12 处视频协议均为 `video` 对象且带 `mimeType`
- 协议注册遗漏 `provider.go` 的 `allowed` 能力映射表，导致"接口类型不支持video生成"
- 只覆盖了部分前端入口，创作页入口未验证

**How to apply:** 
- 任何API协议开发都创建检查清单
- 所有路径字符串必须从文档复制粘贴，不凭记忆
- 新增协议时全局搜索同类协议名（如 `volcengine-ark-video`），逐处确认是否需要同步登记
- 返回格式先 grep 既有实现再动手写
- 没有实际API调用成功证据不交付
- 如无法验证，提前明确告知用户
- 参见 [[docker-verify-deployment-before-testing]]、[[logging-must-cover-full-call-chain]]
