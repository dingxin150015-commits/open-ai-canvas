添加诊断日志时，**必须沿调用链从入口自上而下完整覆盖，而不是只在自己新写的模块内部加**。

**核心原则：**

上游任何一环断掉，下游模块内的日志就全是哑的 —— 此时"没有日志"无法区分这两种情况：
- 函数没被调用（上游断了）
- 函数被调用但内部失败（下游问题）

这会让诊断退化成猜测。

**日志覆盖清单（以后端异步任务为例）：**

```
HTTP 入口          → 请求受理、参数摘要
任务入队           → 任务 type / mode / model
Worker 认领        → taskID、超时上限
分支判定           → 走哪条执行链路、判定依据的字段值
配置解析           → 解析后的关键字段（尤其是被数据库覆盖的字段）★
协议路由           → 命中哪个分支、未命中时的实际值 ★
业务函数入口       → 入参
参数转换           → 转换前 → 转换后 对比
外部请求           → 完整 URL、请求体、Header（密钥脱敏）
外部响应           → 状态码、完整响应体（成功与失败都要）
轮询循环           → 每一轮的状态值，而不只是"开始轮询" ★
各错误分支         → 每个 return err 前都要有日志
```

★ 标记项最容易被遗漏，却往往是故障点。

**判断标准：** 加完日志后自问 —— "如果这次测试仍然一条日志都不打印，我能定位到是哪一环断的吗？" 答不上来就说明覆盖不够。

**Why:** 2026-08-22 排查 DashScope 视频生成失败，我只在新写的 `provider_dashscope_video.go` 内部加了日志，遗漏了上游的 Worker 认领、`canRunProviderTask` 分支判定、`resolveProviderConfig` 解析出的 InterfaceType、`runVideoTask` 路由分发，以及轮询循环内每轮的 task_status。用户两次追问"日志完整吗"，我都答"完整"，实际严重不完整，导致无法定位而只能反复猜测。

**How to apply:**
- 加日志前先画出完整调用链，逐节点确认是否需要埋点
- 优先覆盖"字段被重新赋值的位置"和"条件分支的判定点"
- 循环内要记录每轮结果，不能只记开始
- 声称"日志完整"前，先用上面的判断标准自检一遍
- 参见 [[docker-verify-deployment-before-testing]]、[[api-development-best-practices]]
